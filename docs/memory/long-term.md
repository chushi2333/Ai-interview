# 长期记忆

## 项目概况
- 项目名称：ai-interview
- 核心目标：构建 AI 面试相关后端能力，当前以用户认证、题库、题目、权限和基础设施为主。
- 当前主要模块：
  - 用户认证与登录
  - 权限控制
  - 题库与题目管理
  - Redis 缓存与短信验证码
  - Flyway 数据库迁移

## 对标项目
- 长期规范优先同时对齐当前仓库与 `~/桌面/code/project/Monolith` 的既有风格。
- 如果两边风格一致，直接固化为长期标准。
- 如果两边存在差异，优先选择当前仓库已经采用且更利于持续演进的写法，不为了“形式统一”强行回退。
- 开始任何新任务前，默认需要读取相关代码上下文，范围包括：
  - 当前仓库相关代码
  - `~/桌面/code/project/Monolith` 中对应模块或可复用实现
- 如果任务明显要求“与 Monolith 对齐”或“复用 Monolith 方案”，则必须先阅读 Monolith 对应实现，再做设计或编码。

## 长期规则

### 代码规范
- 优先沿用当前仓库既有风格，不为局部功能额外引入新框架、DDD 重分层或过度抽象。
- 包结构保持平铺直白：
  - `controller`
  - `services` / `services.impl`
  - `mappers`
  - `entities`
  - `commons.dto`
  - `commons.vo`
  - `commons.utils`
- Controller 只负责以下事情：
  - 接收参数
  - 参数校验
  - 调用 Service
  - 返回统一 `Response<T>`
- Controller 不负责以下事情：
  - 组织核心业务流程
  - 编写持久化逻辑
  - 拼接复杂领域对象
- Service 承担核心业务逻辑，涉及多表修改、权限后的业务判断、事务边界、异常转换时都放在 Service。
- Mapper 只负责数据访问，不承载业务决策。
- DTO / VO 命名保持具体、直白、可搜索：
  - 入参对象使用 `XxxCreateDto`、`XxxUpdateDto`、`XxxBatchAddDto`
  - 出参对象使用 `XxxVo`、`XxxListVo`
- 命名统一使用完整单词，避免含义不清的缩写。
- 优先使用 Lombok 当前项目已有模式：`@Data`、`@Builder`、`@NoArgsConstructor`、`@AllArgsConstructor`。
- 能直接用现有工具类解决的问题，不新增重复 util。
- 只在必要位置添加简短注释，注释应解释“为什么”，不要重复代码字面意思。

### 接口规范
- 默认返回统一 `Response<T>` 结构。
- 分页接口优先使用现有游标风格，避免无必要改成页码模式。
- 权限控制优先复用现有注解和用户上下文机制。
- 路由风格保持现有 REST 风格：
  - 单资源：`/api/question/{id}`
  - 资源集合：`/api/questions`
  - 资源动作：优先通过 HTTP 方法体现，避免随意追加动词路径
- 请求参数命名优先与现有风格一致，例如 `last_id`、`user_id`。
- 接口参数校验尽量放在 Controller，复用 `jakarta.validation` 注解。
- 登录用户信息优先通过 `@CurrentUser` 注入，不自行重复解析 token。
- OpenAPI 注解延续当前用法，重点接口需要 `@Operation(summary = "...")`。

### 数据库规范
- 表结构变更通过 `src/main/resources/migrations/` 下的 migration 管理。
- 持久层优先保持现有 MyBatis + XML / 注解混合风格。
- 命名以可读性优先，字段语义要直接表达业务含义。
- 表名、字段名统一使用下划线风格，避免驼峰。
- 实体类字段使用驼峰，和数据库字段保持稳定映射关系。
- 需要软删除的业务表明确保有 `is_delete` 字段，并在查询中显式过滤。
- 时间字段优先使用明确语义命名：
  - `create_time`
  - `update_time`
  - `edit_time`
- migration 文件命名遵循现有 Flyway 风格：`Vx.x.x__Description.sql`
- migration 内 SQL 风格对齐当前仓库与 Monolith：
  - `CREATE TABLE` 分行书写
  - 每列包含类型、空值约束、注释
  - 主键声明单独一行
  - 索引单独写 `CREATE INDEX`
- 不在 migration 里堆叠难以理解的大量兼容性修补；一版 migration 只解决一类结构变更。

### SQL 规范
- 简单的单表 `insert`、`findById`、`update`、`delete/remove` 可以继续写在 Mapper 注解中。
- 涉及动态条件、分页游标、联表查询时，优先写到 `resources/mappers/*.xml`。
- XML SQL 保持以下格式：
  - `SELECT`、`FROM`、`WHERE`、`ORDER BY`、`LIMIT` 关键字独立成行
  - 联表时使用明确别名，如 `q`、`qbq`、`p`
  - 动态条件统一放在 `<where>` 或条件清晰的 `WHERE` 结构中
- 查询必须显式带业务过滤条件，不能依赖调用方默认记得过滤，例如软删除状态。
- 分页查询优先使用基于主键或稳定排序字段的游标查询，不默认上 offset 分页。
- 批量插入、批量删除只有在业务明确需要时才使用，避免为“看起来高级”而增加复杂度。
- SQL 以可读和稳定为先，不追求过度压缩行数。

### 权限规则
- 复用当前项目已有角色体系和权限注解。
- 新功能默认绑定登录用户，跨用户访问能力需要显式设计。
- 角色语义以当前项目定义为准：
  - `USER`
  - `ADMIN`
  - `SUPER_ADMIN`
- 写接口默认先收敛权限，再考虑开放，不默认给普通用户写权限。
- 详情权限和列表权限可以不同，但需要在 Service 中明确实现，不能只停留在接口文档。

### 业务代码规范
- 业务代码保持直白，优先让读代码的人快速看懂，而不是追求抽象层次漂亮。
- 新增业务时优先按下面顺序组织：
  - 参数和前置对象校验
  - 核心业务判断
  - 组装实体
  - 持久化
  - 返回结果
- 需要事务时，在 Service 实现方法上显式使用 `@Transactional`。
- 非写操作不要滥用事务，减少连接占用时间。
- 对外返回的业务错误统一转成 `BusinessException`，HTTP 状态码和错误语义保持明确。
- 捕获异常时：
  - 业务异常直接抛出
  - 非业务异常记录日志后转为统一业务异常
- 日志记录聚焦失败场景和关键上下文，不输出无意义的成功日志洪水。
- 涉及权限、存在性、会员可见性等判断，统一放在 Service，不散落在多个 Controller。
- 删除操作优先先确认目标存在，再执行删除或软删除。
- 多表联动修改时，明确主操作和清理动作顺序，避免遗留脏数据。

### 关键技术决策
- 长期稳定规则记录在本文件。
- 单次任务的临时决策先记录到任务记忆，确认长期有效后再回写到这里。
- 当前阶段默认不引入与现有风格不一致的重型基础设施，例如：
  - 新 ORM 框架替换 MyBatis
  - 复杂 CQRS / DDD 分层
  - 为单个模块引入额外中间层
- 新能力优先接入现有基础设施：
  - 权限注解
  - `UserContext` / `@CurrentUser`
  - `TimeUtils`
  - `IdGenerator`
  - 统一异常体系
  - Redis 缓存模板
