# AI 模块需求分析

## 目标定位

AI 模块不是通用聊天机器人，而是服务于面试刷题和学习复盘的后端能力。

这个模块同时承担两个目标：

- 产品目标：让用户在刷题、复习、模拟面试时得到更具体的学习辅助。
- 学习目标：按顺序掌握 LangChain4j、Prompt、AI Service、Chat Memory、Tool Calling、RAG、MCP 等能力。

因此实现顺序必须从小闭环开始，不能一开始就混合 Agent、RAG 和 MCP。

## 核心原则

- AI 回答必须围绕题库、题解、用户学习行为和面试场景。
- 第一版先验证模型调用和业务上下文拼接，不做复杂智能体。
- RAG 只在需要从大量题目、题解、资料中检索内容时使用。
- Tool Calling 只在 AI 需要主动调用后端业务能力时使用。
- MCP 只在需要连接外部工具、外部资料源或标准化工具协议时使用。
- AI 输出只作为学习建议，不直接修改题目、题解、用户数据。
- API Key、模型名、模型服务地址只放配置或环境变量，不写死在代码里。

## 能力边界

### 不做通用聊天

不提供一个脱离业务上下文的聊天入口。用户不能随便问天气、新闻、生活问题。

### 不让 AI 直接写业务数据

AI 可以生成建议、总结、解释和追问，但不能自动修改题目、题解、错题本、收藏、学习记录。

### 不在第一版做 RAG

当前题目详情页已经能直接拿到题目上下文。只围绕当前题目解释时，不需要向量检索。

### 不在第一版做 MCP

MCP 的价值是把外部系统以标准工具形式接给 AI。当前项目第一阶段只需要调用模型，不需要 MCP。

## 业务场景拆分

### AI 题解助教

入口：题目详情页。

目标：帮助用户理解当前题目和组织面试回答。

输入上下文：

- 题目标题
- 题目内容
- 参考答案
- 题目标签
- 所属题库
- 用户补充问题

能力：

- 大白话解释当前题
- 总结面试回答模板
- 提炼回答重点
- 生成面试官追问
- 根据用户回答给改写建议

第一版只做这个场景。

### AI 模拟面试

入口：

- 题目详情页
- 题库详情页
- 错题本
- 学习档案

目标：围绕一个主题进行多轮问答。

能力：

- 围绕当前题目继续追问
- 围绕题库抽题面试
- 围绕错题查漏补缺
- 对用户回答进行评价
- 用户插话提问后，AI 先解释再拉回面试主题

需要能力：

- Chat Memory
- 面试 Session
- 消息持久化
- 后续可叠加 Tool Calling

### AI 个性化出题

入口：

- 首页
- 错题本
- 学习档案

目标：根据用户学习行为推荐适合继续练习的题目。

能力：

- 分析最近浏览、收藏、错题、自测记录
- 找出薄弱知识点
- 从题库中检索候选题目
- 给出推荐理由

需要能力：

- 学习行为数据查询
- RAG 或混合检索
- Tool Calling

### AI 学习复盘

入口：学习档案。

目标：总结用户最近学习情况，并给出下一步计划。

能力：

- 总结最近 7 天学习情况
- 分析薄弱知识点
- 总结高频错题类型
- 推荐复习方向
- 生成短期学习计划

需要能力：

- 学习行为聚合
- 错题和收藏查询
- 可选 RAG
- 可选 Tool Calling

## 技术概念分层

### LangChain4j

LangChain4j 是 Java 项目接入大模型应用的基础框架。

本项目中优先学习这些能力：

- ChatModel：最基础的模型调用。
- AI Service：把 Prompt 和 Java 接口绑定，减少手写调用代码。
- Chat Memory：支持多轮会话。
- Tool Calling：让模型调用 Java 方法。
- RAG：检索资料后再回答。

### Prompt

Prompt 是第一阶段最重要的工程资产。

第一版需要把 Prompt 明确限制在面试刷题场景：

- 只能基于给定题目上下文回答。
- 不知道时说明缺少资料，不要编造。
- 输出要适合学习和面试表达。
- 不输出和当前题目无关的泛泛内容。

### Tool Calling

Tool Calling 是让 AI 调用后端已有业务能力。

适合场景：

- AI 需要查询题目详情。
- AI 需要查询某个题库下的题目。
- AI 需要查询用户最近学习记录。
- AI 需要查询错题本。
- AI 需要查询收藏题目。

不适合第一版的原因：

- 第一版后端自己已经知道 `questionId`，可以直接查题目后拼 Prompt。
- 不需要让 AI 自己决定调用哪个业务工具。

### RAG

RAG 是 Retrieval-Augmented Generation，核心是先检索，再把检索结果交给模型回答。

需要 RAG 的判断标准：

- 问题答案不只来自当前题目。
- 需要从大量题目、题解、资料中找相关内容。
- 需要根据用户学习行为匹配候选题目。
- 需要引用多个知识片段进行总结。

不需要 RAG 的场景：

- 只解释当前题目。
- 只总结当前题目的面试回答。
- 只基于当前题目的参考答案生成追问。

RAG 需要补的工程能力：

- 文档切分。
- Embedding 模型。
- 向量字段或向量存储。
- 相似度检索。
- 检索结果排序。
- Prompt 拼接。
- 索引重建。
- 检索质量验证。

### MCP

MCP 是 Model Context Protocol，用来把外部工具和外部数据源以统一协议暴露给 AI。

在本项目中，MCP 不作为第一阶段能力。

后续适合 MCP 的场景：

- 接入外部知识库。
- 接入本地文件资料库。
- 接入企业文档、Notion、飞书、GitHub 等外部系统。
- 把项目后端能力作为标准工具开放给其他 AI 客户端。
- 学习 AI 应用如何通过标准协议发现和调用工具。

MCP 和 Tool Calling 的区别：

- Tool Calling 是当前应用内部把 Java 方法交给模型调用。
- MCP 是把工具包装成标准协议，供不同客户端或模型应用调用。

MCP 和 RAG 的区别：

- RAG 解决“从资料中检索什么内容再回答”。
- MCP 解决“模型如何连接和调用外部工具或数据源”。

## 阶段路线

### V1：AI 题解助教

目标：打通后端调用大模型的最小闭环。

接口：

```http
POST /api/ai/question/{questionId}/assist
```

请求：

```json
{
  "type": "simple_explain",
  "userInput": "我不理解缓存击穿"
}
```

`type` 可选值：

- `simple_explain`：大白话解释。
- `interview_answer`：面试回答模板。
- `key_points`：提炼重点。
- `follow_up_questions`：生成追问。
- `answer_polish`：把用户回答改成更适合面试的表达。

返回：

```json
{
  "content": "..."
}
```

实现内容：

- 增加 LangChain4j 依赖。
- 增加 AI 配置项。
- 配置 ChatModel。
- 查询当前题目上下文。
- 根据 `type` 构造 Prompt。
- 同步调用模型。
- 返回文本结果。

不做：

- 不做流式输出。
- 不做多轮会话。
- 不做 RAG。
- 不做 Tool Calling。
- 不做 MCP。
- 不保存 AI 消息记录。

验收标准：

- 后端能基于指定题目返回 AI 解释。
- 不传 API Key 时应用能给出明确配置错误。
- 题目不存在时返回业务错误。
- AI 回答不会脱离题目上下文。

### V2：AI 助教输出结构化

目标：让前端更容易展示 AI 结果。

能力：

- 面试回答模板按段落输出。
- 重点列表按数组输出。
- 追问按列表输出。
- 可选择保留纯文本接口。

需要学习：

- LangChain4j 结构化输出。
- 输出解析失败时的兜底策略。

### V3：模拟面试会话

目标：支持多轮面试对话。

接口：

```http
POST /api/ai/interview/session
POST /api/ai/interview/session/{sessionId}/message
```

实现内容：

- 增加面试 Session 表。
- 增加消息表。
- 引入 Chat Memory。
- 支持用户回答、用户追问、AI 评价、AI 追问。

不做：

- 不从全题库自由检索。
- 不做个性化推荐。

### V4：Tool Calling

目标：让 AI 可以主动查询后端已有业务能力。

候选工具：

- 查询题目详情。
- 查询题库题目列表。
- 查询用户错题。
- 查询用户收藏。
- 查询最近学习记录。

适用场景：

- 模拟面试过程中，AI 需要临时查另一道相关题。
- 学习复盘时，AI 需要读取用户学习数据。
- 个性化出题时，AI 需要获取候选题目。

验收标准：

- 工具只能读取数据，不写业务数据。
- 工具调用参数必须可校验。
- 用户只能查询自己有权限的数据。

### V5：RAG 题库检索

目标：让 AI 基于题库和题解检索后回答。

实现内容：

- 把题目标题、内容、答案、标签切成可检索文档。
- 生成 Embedding。
- 存储向量索引。
- 根据用户问题检索相关片段。
- 把检索片段拼入 Prompt。
- 返回带检索依据的回答。

优先服务：

- 题库范围模拟面试。
- 相似题推荐。
- 个性化出题。
- 学习复盘。

### V6：MCP

目标：学习标准化工具协议，并为后续外部系统接入做准备。

可能方向：

- 做一个本项目自己的 MCP Server，暴露只读工具。
- 工具包括查询题目、查询题库、查询用户学习摘要。
- 让外部 AI 客户端通过 MCP 调用本项目能力。
- 或者接入外部 MCP Server，把外部资料源接入 AI 模块。

不作为早期功能上线目标，作为学习和扩展阶段。

## 从零开始的实现顺序

### 第一步：只接模型

目标：确认项目能调用模型。

最小动作：

- 加 LangChain4j 模型依赖。
- 配置 `OPENAI_API_KEY` 或兼容模型服务配置。
- 写一个内部测试 Service。
- 调一次简单 Prompt。

### 第二步：接业务上下文

目标：让模型回答当前题目。

最小动作：

- 通过 `questionId` 查询题目。
- 组合题目标题、内容、答案、标签。
- 按 `type` 选择 Prompt 模板。
- 返回 AI 文本。

### 第三步：整理 Prompt 模板

目标：让输出稳定。

最小动作：

- 为每种 `type` 定义独立模板。
- 限制回答范围。
- 约束输出风格。
- 加兜底规则。

### 第四步：再考虑会话

目标：支持模拟面试。

只有当单轮助教稳定后，再做多轮。

### 第五步：再考虑工具和检索

目标：让 AI 不只回答当前题。

当需要跨题库、跨错题、跨学习记录时，再上 Tool Calling 和 RAG。

### 第六步：最后学习 MCP

目标：理解外部工具协议。

当内部 Tool Calling 和 RAG 已经清楚后，再做 MCP，否则会把几个概念混在一起。

已有能力：

- 用户认证。
- 题目管理。
- 题库管理。
- 题库题目关系。
- 题目搜索。
- 自测记录。
- 错题本。
- 收藏题目。
- 学习记录。
- MySQL。
- Redis。
- RabbitMQ。
- Elasticsearch。
- SeaweedFS。

V1 只依赖：

- 题目查询。
- 用户权限。
- 大模型调用。

V1 暂不依赖：

- Redis。
- RabbitMQ。
- Elasticsearch。
- SeaweedFS。
- RAG。
- MCP。

## 推荐开发顺序

1. 重写并确认 AI 模块需求。
2. 接入 LangChain4j 基础模型调用。
3. 实现 AI 题解助教同步接口。
4. 优化 Prompt 和输出格式。
5. 增加模拟面试会话。
6. 增加 Tool Calling。
7. 增加 RAG 题库检索。
8. 增加个性化出题和学习复盘。
9. 学习并接入 MCP。
